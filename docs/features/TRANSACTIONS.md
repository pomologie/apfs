# APFS mutable engine, advanced capabilities and Charles (A-MUT-01 through A-MUT-04)

This is a long-term independently scoped roadmap. APFS mutation is substantially harder than a fresh constructor. Do not enable mutable mounts merely because a raw image can be generated. Require exclusive device, supported volume/container feature profile, durable block barriers, versioned immutable read views and explicit transaction ownership. First mutable milestones operate on disposable image files; no physical system disks. Develop detailed invariant and crash model before writing live metadata.

## Copy-on-write transaction design

Begin from a selected fully validated committed checkpoint XID. Transaction allocates new blocks and objects without mutating blocks reachable from any retained checkpoint/snapshot/clone, stages filesystem-tree changes and object-map updates with new transaction identity, maintains extent references, allocator/spaceman counts, free queues, reaper and deferred frees. Key-value B-tree path copying, node split/merge, correct parent/root publication and map generation; no stale mapping use. Data write/truncate/extend, create/remove/rename/link/xattr operations, directory semantics and permissions, sparse extents; transaction failures roll back reservations without freeing reachable data. Concurrency model initially one writer, readers pin immutable checkpoint; locks/order/cache invalidation explicit. Generation and ID allocation checked; no wrap silently. Commit dependencies durable before publishing root/checkpoint; write complete new mapping and descriptor/data checkpoint state, issue correct barriers and update bootstrap/retirement only under validated format ordering. Exact Apple checkpoint commit protocol must be derived and qualified, not assumed from generic CoW algorithm. Maintain old checkpoint until newest complete valid commit durable. Reclamation safe only when no retained references; never free shared extents from live clones/snapshots, including pending/reaper state. Abort doesn't publish partial view; on open detect torn checkpoint and recover read-only to valid one with diagnostic. No promise whole multi-file transaction atomicity beyond qualified scope. Test power interruption, reordered/dropped/torn writes within documented device guarantees, ENOSPC, repeated transactions crossing descriptor ring, deferred-free exhaustion, concurrent read pinned older XID, recovery to last valid commit, native fsck/mount and mutation on copies. Formal reachability/allocation invariants and reference oracle mandatory.

## Snapshots, clones and multi-volume management

Read snapshots first. Snapshot create/delete/restore and pinning require coherent snapshot trees, XID views, object-map references and space-management/reaper updates; prove no dangling mappings and correct reclamation. Clones create shared physical extents with reference accounting, isolate on modification (CoW), preserve original bytes after either mutation/deletion. Verify partial extent split, truncation, clone chain, snapshot+clone overlap, crash and refcount underflow prevention. Multiple volumes share container space; quotas/reserves/role/group semantics require explicit policy and evidence. Test storage accounting under pressure and transactions; no independent per-volume allocation maps that double-count free space. Advanced dedup not a goal unless independently specified. Resizing, compaction, reclaim and repair only if separately scoped and qualified; no forensic suite.

## Encryption, sealing and boot-related features

Authorized encryption read/write is separate from DMG container encryption. Identify keybag, wrapping, crypto IDs, per-file/volume encryption semantics using lawful fixtures and vetted crypto libraries; explicit user-provided credentials, bounded KDF, zeroized secrets/caches, no credential guessing, no bypass of security protections. Validate correct/wrong password, corrupted records, missing keys, unsupported algorithms, key lifecycle and actual interoperability; do not claim authentication beyond mode. Sealed volume read may expose metadata and verify qualified hash/integrity structures independently; does not imply Apple's secure boot trust or authorization to produce a trusted Apple seal. Fusion/multi-store address mapping separate storage profile with exhaustive tests; do not guess. System volume groups/roles, boot metadata, EFI jumpstart and signed-system-volume mechanisms are research-gated, not initial dmgez features. Use independent Charles trust policy, no redistribution of Apple firmware/proprietary code, no bypass of Apple security. Targeted patent/IP review before commercialization of advanced features.

## Charles integration

Adapt generic block I/O to kernel driver/VFS, allocator, synchronization, page/cache, power management, permissions, namespaces, concurrency and cancellation. `no_std + alloc` core is only a prerequisite; qualify actual block barriers, atomicity assumptions, fault behavior, hot unplug and mount lifecycles. Charles is a consumer, not part of this repo. Boot-compatible system volumes and OS framework behavior belong in Charles's own design with separate legal/security review. No full macOS compatibility promise from APFS itself. Stage end-to-end tests on disposable virtual/physical test storage without risking real data. The independent APFS project can ship a reliable limited reader before any of this work.

# APFS release evidence

Run the checker with Python 3.11 or later and Git from a clean candidate worktree. Keep the bundle and its transcripts outside that worktree.

```sh
python3 -B tools/check_release_evidence.py --root . --bundle "$evidence_dir/bundle.json"
```

The release command derives the mandatory method matrix for the milestone from the committed [obligation registry](obligations.json), then requires evidence for every invocation in the committed [release policy](release-profile.json). The format Kani and checkpoint TLC invocations cover their configured methods. The policy also includes partial invocations for property, fuzz, differential and native evidence. The full release command requires complete profiles for all active methods.

Use `--method A-V01/property` with a bundle containing the six property records for the same clean revision. The checker requires the named bootstrap, locator, range, native-window, five-size native-window, and generated-object profiles. Together they cover declared geometry, both locator layouts, collections of up to eight ranges, object headers and checksum windows, and refusal before unsupported checkpoint traversal. The bootstrap transcript verifies the read cutoff for inadmissible geometry at all five block sizes and for unsupported checkpoint features in both open modes. Fuzz, differential, and native qualification retain separate release gates.

The checker accepted the six-profile property bundle at clean revision `be236d8`. It rejected a control bundle missing the generated-object receipt and still reported seven incomplete A-V01 and A-V02 methods when evaluating the full release gate. The bundle and logs are in `target/verification-evidence/v0.1.0/be236d8-a-v01-property/`. The bundle SHA-256 is `bde02b1aebeebaaaafcc12567fd56065e877a04e6ac3ade1db3a12af6dfbacbe`.

Use `--method A-V01/differential` with the four differential receipts from the same clean revision. The bootstrap comparison uses an independent Python model of widened extent arithmetic, little-endian header fields, Fletcher-64, and feature admission. It checks 455 production observations, including typed refusal cases. The other three profiles compare checksum patterns and native wire layouts, including both checkpoint areas and all five block sizes. Fuzz and native methods remain separate release gates. [Bootstrap oracle](../crates/container/apfs-container/verification/bootstrap_wire_oracle.py)

Use `--method A-V02/property` with the checkpoint model, layout, and typed decision receipts for the same revision. The typed matrix covers two descriptor positions, three possible XIDs, seven states per position, and automatic or exact selection. It compares decisions, candidate attempt order, and diagnostics for all 1,764 cases. The other receipts exercise actual checkpoint reads with the two-candidate model and larger rings. Native, fuzz, and differential evidence have separate gates. [Typed decision model](../crates/container/apfs-container/src/checkpoint/decision_tests.rs)

Use `--profile` with a profile name to check one invocation independently. Run the profile command from the candidate root with the pinned tools and capture stdout and stderr in one artifact. The bundle is a JSON array of [schema v1 records](evidence.schema.json). Set `commit` to the Git commit and `source_hash` to the SHA-256 of the archive below. It binds the committed source, runner, and verification policy to the record, with the Git line ending settings pinned across platforms.

```sh
git -c tar.umask=0002 -c core.autocrlf=false -c core.eol=lf archive --format=tar HEAD | shasum -a 256
```

Use the policy’s `command`, `features` and `bounds` values. Record the runner, measured duration, exact tool versions and exit code. Include a `transcript` artifact with its SHA-256 and a path relative to the bundle. For Kani and TLC profiles, set `proof.theorem` to the profile name.

The format profile uses `bash crates/formats/apfs-format/verification/check.sh`. The checker verifies each required Kani harness and cover count.

The `format-checksum-differential` profile uses `bash crates/formats/apfs-format/verification/check-checksum.sh`. It requires all seven named native fixture results with their expected wire checksums, plus every uniform and single changed word case across the five admitted sizes. The comparison uses the independent weighted-sum oracle in the integration tests. This covers the Fletcher-64 arithmetic subset of A-V01.

The `format-native-geometry-differential` profile uses `bash crates/formats/apfs-format/verification/check-native-geometry.sh`. Set `fixture_hash` to `geometry_cases.ledger_sha256`. The runner verifies five unmodified 4 KiB fixture blocks against the Sonoma acquisition ledger, including each stored checksum. It compares 25 rows from checksum-verified Rust decodes against an independent Python wire decoder and widened arithmetic. The rows cover three NXSB geometries, six ring descriptions, two checkpoint map summaries, six mapped byte extents, five complete object headers, and three NXSB feature profiles. Those profiles include the optional, read-only-compatible, and required masks and the keylocker and fragmented-area qualifiers. The checker verifies the exact row counts and a digest of every compared value. This partial profile covers accepted native objects using version two and contiguous rings. [Wire oracle](../crates/formats/apfs-format/verification/native_geometry_oracle.py) · [Apple File System Reference, Container and checkpoint maps](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf#page=40)

The `format-native-size-matrix-differential` profile adds `--size-matrix` to the same runner. It compares 25 rows from retained superblocks of five 128 MiB Sonoma containers spanning all admitted block sizes. The independent oracle checks Fletcher-64 and compares the complete headers, feature profiles, container geometry, the object-map locator and its block extent, and the fields and byte bounds of both contiguous checkpoint rings. Use `geometry_cases.ledger_sha256` as `fixture_hash`. This partial profile covers intact block-zero captures. Checkpoint-map evidence comes from the separate 4 KiB comparison. The runner reads the retained files and executes no native filesystem commands. [Acquisition ledger](../crates/container/apfs-container/tests/fixtures/native-bootstrap-sizes/acquisition.json) · [Production decode reporter](../crates/formats/apfs-format/tests/native_geometry.rs)

The `bootstrap-properties` profile runs the [deterministic bootstrap boundary matrix](../crates/container/apfs-container/tests/bootstrap_properties.rs). It compares NXSB admission and range endpoints against widened arithmetic, checks all header and checksum window prefix lengths through 64 bytes, and adds each of the 63 other feature bits to the supported native feature word. The [typed admission matrix](../crates/container/apfs-container/src/checkpoint/tests.rs) exhausts every zero-, one-, and two-bit subset of the 63 other required bits, with version two present or absent. It checks all four combinations of keylocker and fragmented-area qualifiers for each of the 4,034 masks against an independent set-membership model. This adds 16,136 typed decisions, including the exact error and its precedence. The typed test uses an unchanged native header as its starting profile and performs no device access.

The same profile tests the traversal cutoff for four required-mask cases (missing version two, either of two additional bits, and both bits) crossed with optional defragmentation and a read-only-compatible extension bit, each present or absent. At each of the five supported sizes, both open modes return the full refused mask, block-zero address, and expected XID after exactly two reads of block zero. They receive 80 complete checksummed bootstrap objects in memory, for 160 open attempts. The `complete-object-properties` profile separately verifies supported required masks and generated compatible masks at the same sizes. Qualification of mixed feature masks on checkpoint descriptors is a separate selection concern.

The `geometry-span-properties` profile generates collections of zero through eight valid block spans. It uses the unmodified Sonoma bootstrap geometry and complete synthetic NXSB objects for each of the five supported block sizes. Each generated case also checks the whole container, its last block, and the empty range at the end. A widened arithmetic model computes both byte endpoints independently. Use seed `"7"` in the evidence record. The checker requires 64 generated cases per source, block size, and entry count, plus exactly three boundary ranges per case. [Range properties](../crates/formats/apfs-format/tests/locator_properties.rs)

The `native-checksum-window-properties` profile runs `bash crates/formats/apfs-format/verification/check-native-windows.sh`. It compares all five verified header fields against their wire offsets for each of the seven unmodified 4 KiB Sonoma objects. The Fletcher-64 oracle then checks each aligned prefix from 32 bytes through the full object, and the type hint must match the native header on every prefix. The checker requires 1,017 observations and the native stored checksum for each fixture. This partial profile covers 7,119 native checksum windows. [Checksum window tests](../crates/formats/apfs-format/tests/checksum.rs)

The `native-size-matrix-window-properties` profile runs the same checker with `--size-matrix`. It tests every prefix of each of the five unchanged Sonoma block-zero fixtures at 4–64 KiB, including the empty prefix. A widened payload sum and first moment determine both Fletcher check words for all 31,709 admitted checksum windows. The header check accepts exactly those windows whose computed checksum matches the stored value. The other 95,272 requests must return typed truncation from both checksum and header verification. All 126,981 prefixes check the independent type-field cutoff at 28 bytes. Use `window_cases.ledger_sha256` as `fixture_hash`. The runner validates each retained block against the acquisition ledger and the checker requires exact per-size counts and stored checksums. This partial property profile covers the checksum and header windows on retained block-zero bytes. [Acquisition ledger](../crates/container/apfs-container/tests/fixtures/native-bootstrap-sizes/acquisition.json) · [Window tests](../crates/formats/apfs-format/tests/checksum.rs)

The `format-request-fuzz` profile runs the [format request fuzzer](../crates/formats/apfs-format/verification/fuzz/check-format-requests.sh) with AddressSanitizer. It starts with 58 scalar requests and runs 20,000 libFuzzer iterations with seed `"7"` and a 17-byte input limit. The requests choose a prefix length on one of seven unchanged native objects or a block range in the retained 4 KiB geometry. The fuzzer compares accepted and refused requests against wire alignment and independent `u128` checksum and range calculations. This partial profile covers bounded request arithmetic on retained objects. Real object sizes beyond 4 KiB and fuzzed object decoding remain outside its scope.

The `complete-object-properties` profile generates 64 complete synthetic NXSB objects at each of the five admitted block sizes. An independent weighted sum supplies the stored checksum. The production decoder must then recover the generated transaction, declared container geometry, and in-range object-map address. Each case compares five checksum windows and three byte ranges against widened arithmetic. It also crosses four optional masks (none, defragmentation, one generated extension bit, and both bits) with two read-only-compatible masks (none and one generated extension bit). Each independently checksummed version-two object must preserve both masks and retain the same verified required profile. Apple specifies that optional features may be ignored and that unknown read-only-compatible features permit read-only access. Use seed `"7"` in the evidence record. The independent native replay covers the retained Apple objects. Generated combinations involving unknown required flags remain outside this profile. [Complete NXSB properties](../crates/formats/apfs-format/tests/locator_properties.rs) · [Apple File System Reference, pp. 29, 37–38](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf)

The `bootstrap-native` profile replays the retained 4 KiB-block Sonoma fixture with `bash crates/filesystem/apfs-reader/verification/check-native-bootstrap.sh`. Set `fixture_hash` to the policy’s `native_fixture.ledger_sha256` value. The runner verifies the acquisition ledger in LF form and the hashes of the retained metadata blocks, block zero, and filesystem root. The checker binds the transcript to the recorded successful Apple `fsck_apfs -n` invocation, its XID 4 result, and the original image digest. It also requires a fresh production replay with the same checkpoint, 64 MiB extent, wire checksum, and exact read counts for each typed bootstrap refusal. The Apple invocation comes from the fixture’s recorded acquisition. The runner uses the retained blocks and needs no mount. This partial native profile covers the populated bootstrap case. [Acquisition ledger](../crates/filesystem/apfs-reader/tests/fixtures/sonoma-populated-fsroot.json) · [Replay tests](../crates/filesystem/apfs-reader/tests/view/bootstrap.rs)

The `bootstrap-native-128m` partial profile verifies the retained Sonoma block-zero digest against its acquisition ledger and checks Apple’s recorded read-only XID 2 observation. It replays production extent probing with the native 128 MiB source length and with 1,024 trailing bytes. Both observations require a 40-byte prefix and one 4 KiB block read at byte zero. Use `native_extent.ledger_sha256` as the record’s `fixture_hash`. The profile covers block-zero recognition and extent arithmetic. The `bootstrap-native-size-matrix` partial profile checks five unchanged native block-zero captures at 4, 8, 16, 32, and 64 KiB. The runner checks ledger hashes and the recorded read-only Apple checker result for each capture, verifies the version-two wire geometry, and compares production results for the exact and padded source lengths. Use `native_size_matrix.ledger_sha256` as the record’s `fixture_hash`. This adds positive bootstrap evidence at all admitted block sizes. Other A-V01 native scenarios remain open. The `locator-properties` profile runs [generated NXSB locator cases](../crates/formats/apfs-format/tests/locator_properties.rs) with Proptest 1.12.0 and the schema seed string `"7"`. It checks both layouts and all five supported sizes. Each layout and block-size pair runs 64 cases for each of seven locator scenarios. The widened model decides admission, validates the decoded fields and compares the checked physical byte range. Fragmented locators are recognized by the codec. Opening a fragmented container remains outside the supported profile. This is the generated locator subset of A-V01 property evidence and remains separate from the bootstrap prefix matrix.

The checkpoint profile uses `bash crates/container/apfs-container/verification/models/check-evidence.sh`. Set `TLA2TOOLS_JAR` to the pinned TLA+ Tools v1.7.4 JAR and use Java 21.0.8. The runner validates the JAR digest, checks the committed model, and checks a temporary model with the documented wrong-selection witness. Record the profile seed as the schema string `"0"` and include `states` and `distinct_states` from the policy in `proof`. The checker verifies the full state graph, temporal check, and expected invariant violation with a counterexample.

The `checkpoint-model-properties` profile compares production selection and diagnostics with the [Rust reference model](../crates/container/apfs-container/verification/checkpoint_selection.rs). It requires every pair of earlier and latest states under automatic selection, exact XID 1, and exact XID 2. The 147 cases share two candidates and one wrapped descriptor-ring fixture.

The `checkpoint-layout-properties` profile compares valid production selection with an independent placement plan. It checks 45 layouts and all 180 automatic and exact requests for one, three and four complete candidates. It varies descriptor rings of 8, 16 and 32 slots, inserts candidates at the start, middle and wrap positions, and uses both XID orders when there is more than one candidate. It compares the selected XID, physical descriptor and ephemeral payload addresses. Both profiles provide bounded property and reference-comparison evidence for A-V02. The larger rings cover complete candidates, with damage and fallback permutations exercised by the two-candidate model. [Valid layout matrix](../crates/container/apfs-container/verification/checkpoint_layouts.rs)

The `checkpoint-native-replay` profile validates the two retained Sonoma acquisition ledgers and packed fixtures, then replays automatic and exact checkpoint selection across descriptor slot reuse. It requires Apple’s recorded read-only checker results at XIDs 4 and 6, plus the observed descriptor addresses, ring slots, and mapped payload addresses. Use the ordered digest of the two ledger hashes from `native_checkpoints.ledger_set_sha256` as `fixture_hash`. This profile covers the retained positive native cases. Native straddling and damaged-checkpoint witnesses remain separate A-V02 evidence. [Checkpoint replay](../crates/filesystem/apfs-reader/tests/view/native_checkpoints.rs)

The `checkpoint-native-full-open` partial A-V02 profile formats five fresh 128 MiB regular files on the pinned macOS host. The checker binds the JSON transcript to the acquisition runner and Rust harness at the candidate revision. For every block size it rechecks Apple’s read-only XID and volume UUID against the Rust automatic and exact selection results, with identical image digests before and after the checks. Use the JSON output as the transcript artifact. Fresh UUIDs and image hashes belong to each invocation, and this profile omits `fixture_hash`. Native ring straddling and fallback remain separate release evidence. [Acquisition runner](../crates/container/apfs-container/verification/check_native_checkpoint_open.py)

The `checkpoint-native-differential` profile reuses the same fixture policy and `fixture_hash`. An independent Python scan reads all four descriptor and map pairs in each eight-slot ring and checks their wire checksums and mapping spans. It verifies the newest candidate’s retained payload and object-map headers and compares the production selection facts with the native acquisition result. The comparison covers the two retained positive snapshots. Older candidates contribute descriptor and map evidence, with retained payload coverage for the selected XIDs. Broader differential coverage remains open for A-V02. [Wire comparator](../crates/filesystem/apfs-reader/verification/compare_native_checkpoints.py)

## Architecture and coverage

The Rust source check enforces structural `lib.rs` and `mod.rs` files and the 500-line limit for every tracked or nonignored Rust source. The kernel dependency regression runs both bare-metal targets and checks that a host-only proc macro dependency stays out of the target-side graph. [Rust source check](../tools/check_rust_roots.py) · [Kernel graph regression](../tools/test_check_kernel_dependencies.py)

From a clean candidate, collect source-based line and branch counts with `python3 -B tools/measure_coverage.py --output "$evidence_dir"`. The collector uses `nightly-2026-11-04`, its bundled `llvm-tools`, and Nextest 0.9.151. It runs the locked no-default-features workspace suite, merges the test profiles, and reports covered and total lines and branches for owned production paths. It requires coverage data for NXSB geometry, object headers, bootstrap admission, checkpoint maps, selection, and validation. The output includes exact candidate and tool versions. Evaluate the counts against the proposed EVS-1 thresholds per critical source. A file with zero mapped branch outcomes has line evidence only. [Coverage collector](../tools/measure_coverage.py) · [EVS-1 thresholds](../docs/architecture/ECOSYSTEM_VERIFICATION.md#7-ci-and-quantitative-gates)

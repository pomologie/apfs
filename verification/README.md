# APFS release evidence

Run the checker with Python 3.11 or later and Git from a clean candidate worktree. Keep the bundle and its transcripts outside that worktree.

```sh
python3 -B tools/check_release_evidence.py --root . --bundle "$evidence_dir/bundle.json"
```

The release command derives the mandatory method matrix for the milestone from the committed [obligation registry](obligations.json), then requires evidence for every invocation in the committed [release policy](release-profile.json). The policy defines the format Kani invocation for A-V01, the checkpoint TLC invocation for A-V02, and partial invocations for A-V01 checksum comparison, generated and directed properties, and native bootstrap replay. The full release command requires complete profiles for all active methods.

Use `--profile` with a profile name to check one invocation independently. Run the profile command from the candidate root with the pinned tools and capture stdout and stderr in one artifact. The bundle is a JSON array of [schema v1 records](evidence.schema.json). Set `commit` to the Git commit and `source_hash` to the SHA-256 of the archive below. It binds the committed source, runner, and verification policy to the record, with the Git line ending settings pinned across platforms.

```sh
git -c tar.umask=0002 -c core.autocrlf=false -c core.eol=lf archive --format=tar HEAD | shasum -a 256
```

Use the policy’s `command`, `features` and `bounds` values. Record the runner, measured duration, exact tool versions and exit code. Include a `transcript` artifact with its SHA-256 and a path relative to the bundle. For Kani and TLC profiles, set `proof.theorem` to the profile name.

The format profile uses `bash crates/formats/apfs-format/verification/check.sh`. The checker verifies each required Kani harness and cover count.

The `format-checksum-differential` profile uses `bash crates/formats/apfs-format/verification/check-checksum.sh`. It requires all seven named native fixture results with their expected wire checksums, plus every uniform and single changed word case across the five admitted sizes. The comparison uses the independent weighted-sum oracle in the integration tests. This covers the Fletcher-64 arithmetic subset of A-V01.

The `format-native-geometry-differential` profile uses `bash crates/formats/apfs-format/verification/check-native-geometry.sh`. Set `fixture_hash` to `geometry_cases.ledger_sha256`. The runner verifies five unmodified fixture blocks against the Sonoma acquisition ledger. It compares checksum-verified Rust decodes with an independent Python wire decoder and integer arithmetic for three NXSB blocks, six ring descriptions, two map headers, and six mapped byte extents. The checker verifies the exact row counts and a digest of all compared rows. This partial profile covers the accepted native geometry. [Wire oracle](../crates/formats/apfs-format/verification/native_geometry_oracle.py) · [Apple File System Reference, Container and checkpoint maps](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf#page=40)

The `bootstrap-properties` profile runs the [deterministic bootstrap boundary matrix](../crates/container/apfs-container/tests/bootstrap_properties.rs). It compares NXSB admission and range endpoints against widened arithmetic, checks all header and checksum window prefix lengths through 64 bytes, and adds each of the 63 other feature bits to the supported native feature word. The checker requires a row for every supported block size and the named prefix, checksum and feature cases. This profile covers selected bootstrap boundaries. Broader generated input and checkpoint area combinations are separate evidence.

The `geometry-span-properties` profile generates collections of zero through eight valid block spans. It uses the unmodified Sonoma bootstrap geometry and complete synthetic NXSB objects for each of the five supported block sizes. Each generated case also checks the whole container, its last block, and the empty range at the end. A widened arithmetic model computes both byte endpoints independently. Use seed `"7"` in the evidence record. The checker requires 64 generated cases per source, block size, and entry count, plus exactly three boundary ranges per case. [Range properties](../crates/formats/apfs-format/tests/locator_properties.rs)

The `native-checksum-window-properties` profile runs `bash crates/formats/apfs-format/verification/check-native-windows.sh`. It compares all five verified header fields against their wire offsets for each of the seven unmodified 4 KiB Sonoma objects. The Fletcher-64 oracle then checks each aligned prefix from 32 bytes through the full object, and the type hint must match the native header on every prefix. The checker requires 1,017 observations and the native stored checksum for each fixture. This partial profile covers 7,119 native checksum windows. [Checksum window tests](../crates/formats/apfs-format/tests/checksum.rs)

The `complete-object-properties` profile generates 64 complete synthetic NXSB objects at each of the five admitted block sizes. An independent weighted sum supplies the stored checksum. The production decoder must then recover the generated transaction, declared container geometry, and in-range object-map address. Each case compares five checksum windows and three byte ranges against widened arithmetic. It also crosses four optional masks (none, defragmentation, one generated extension bit, and both bits) with two read-only-compatible masks (none and one generated extension bit). Each independently checksummed version-two object must preserve both masks and retain the same verified required profile. Apple specifies that optional features may be ignored and that unknown read-only-compatible features permit read-only access. Use seed `"7"` in the evidence record. The independent native replay covers the retained Apple objects. Generated combinations involving unknown required flags remain outside this profile. [Complete NXSB properties](../crates/formats/apfs-format/tests/locator_properties.rs) · [Apple File System Reference, pp. 29, 37–38](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf)

The `bootstrap-native` profile replays the retained 4 KiB-block Sonoma fixture with `bash crates/filesystem/apfs-reader/verification/check-native-bootstrap.sh`. Set `fixture_hash` to the policy’s `native_fixture.ledger_sha256` value. The runner verifies the acquisition ledger in LF form and the hashes of the retained metadata blocks, block zero, and filesystem root. The checker binds the transcript to the recorded successful Apple `fsck_apfs -n` invocation, its XID 4 result, and the original image digest. It also requires a fresh production replay with the same checkpoint, 64 MiB extent, wire checksum, and exact read counts for each typed bootstrap refusal. The Apple invocation comes from the fixture’s recorded acquisition. The runner uses the retained blocks and needs no mount. This partial native profile covers the populated bootstrap case. [Acquisition ledger](../crates/filesystem/apfs-reader/tests/fixtures/sonoma-populated-fsroot.json) · [Replay tests](../crates/filesystem/apfs-reader/tests/view/bootstrap.rs)

The `locator-properties` profile runs [generated NXSB locator cases](../crates/formats/apfs-format/tests/locator_properties.rs) with Proptest 1.12.0 and the schema seed string `"7"`. It checks both layouts and all five supported sizes. Each layout and block-size pair runs 64 cases for each of seven locator scenarios. The widened model decides admission, validates the decoded fields and compares the checked physical byte range. Fragmented locators are recognized by the codec. Opening a fragmented container remains outside the supported profile. This is the generated locator subset of A-V01 property evidence and remains separate from the bootstrap prefix matrix.

The checkpoint profile uses `bash crates/container/apfs-container/verification/models/check-evidence.sh`. Set `TLA2TOOLS_JAR` to the pinned TLA+ Tools v1.7.4 JAR and use Java 21.0.8. The runner validates the JAR digest, checks the committed model, and checks a temporary model with the documented wrong-selection witness. Record the profile seed as the schema string `"0"` and include `states` and `distinct_states` from the policy in `proof`. The checker verifies the full state graph, temporal check, and expected invariant violation with a counterexample.

The `checkpoint-model-properties` profile compares production selection and diagnostics with the [Rust reference model](../crates/container/apfs-container/verification/checkpoint_selection.rs). It requires every pair of earlier and latest states under automatic selection, exact XID 1, and exact XID 2. The 147 cases share two candidates and one wrapped descriptor-ring fixture.

The `checkpoint-layout-properties` profile compares valid production selection with an independent placement plan. It checks 45 layouts and all 180 automatic and exact requests for one, three and four complete candidates. It varies descriptor rings of 8, 16 and 32 slots, inserts candidates at the start, middle and wrap positions, and uses both XID orders when there is more than one candidate. It compares the selected XID, physical descriptor and ephemeral payload addresses. Both profiles provide bounded property and reference-comparison evidence for A-V02. The larger rings cover complete candidates, with damage and fallback permutations exercised by the two-candidate model. [Valid layout matrix](../crates/container/apfs-container/verification/checkpoint_layouts.rs)

The `checkpoint-native-replay` profile validates the two retained Sonoma acquisition ledgers and packed fixtures, then replays automatic and exact checkpoint selection across descriptor slot reuse. It requires Apple’s recorded read-only checker results at XIDs 4 and 6, plus the observed descriptor addresses, ring slots, and mapped payload addresses. Use the ordered digest of the two ledger hashes from `native_checkpoints.ledger_set_sha256` as `fixture_hash`. This profile covers the retained positive native cases. Native straddling and damaged-checkpoint witnesses remain separate A-V02 evidence. [Checkpoint replay](../crates/filesystem/apfs-reader/tests/view/native_checkpoints.rs)

The release process supplies the logs from the actual invocations. Profile passes and the standalone checker tests are partial evidence for A-VER-02-T01. [Checker tests](../tools/test_check_release_evidence.py)

## Architecture and coverage

The Rust source check enforces structural `lib.rs` and `mod.rs` files and the 500-line limit for every tracked or nonignored Rust source. The kernel dependency regression runs both bare-metal targets and checks that a host-only proc macro dependency stays out of the target-side graph. [Rust source check](../tools/check_rust_roots.py) · [Kernel graph regression](../tools/test_check_kernel_dependencies.py)

From a clean candidate, collect source-based line and branch counts with `python3 -B tools/measure_coverage.py --output "$evidence_dir"`. The collector uses `nightly-2026-11-04`, its bundled `llvm-tools`, and Nextest 0.9.151. It runs the locked no-default-features workspace suite, merges the test profiles, and reports covered and total lines and branches for owned production paths. It requires coverage data for NXSB geometry, object headers, bootstrap admission, checkpoint maps, selection, and validation. The output includes exact candidate and tool versions. Evaluate the counts against the proposed EVS-1 thresholds per critical source. A file with zero mapped branch outcomes has line evidence only. [Coverage collector](../tools/measure_coverage.py) · [EVS-1 thresholds](../docs/architecture/ECOSYSTEM_VERIFICATION.md#7-ci-and-quantitative-gates)

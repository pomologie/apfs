# APFS filesystem reader

`VolumeView` opens an explicitly selected ordinary volume using its checkpoint-bound volume object map. It checks the root inode, reads inode metadata and declared data-stream sizes, pages through directory records in on-disk order, and looks up names by their stored UTF-8 bytes. Exact lookup also checks the target inode. Directory paging checks the declared child count and uses a cursor scoped to the container, volume, checkpoint, and directory. Each page scans the matching directory records under traversal and aggregate object-read budgets.

The admitted virtual filesystem tree uses variable-sized key/value slots and standard checksummed object headers in an ordinary unencrypted volume. Traversal checks object identity and storage, occupied slot bounds and overlap, inode/type ordering, split-child routing, and repeated references in the visited nodes. Filesystem-node free-list head locations are checked for bounds. [Apple File System Reference](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf)

`open_file` admits a regular file with continuous logical extents and an unshared data stream. Every data range must map to owning, checksummed records from the selected physical extent-reference tree and avoid the known checkpoint and volume metadata blocks. `FileData::read_exact_at` reads within the logical file length. Metadata and payload reads share the volume budget. `read_link` returns the bytes of an inline symbolic-link target. Sparse, cloned or shared, compressed, and encrypted data states return typed unsupported errors. Filesystem Unicode equivalence, hashed-node verification, and whole-volume consistency checking remain future profiles.

`list_xattrs` pages through the stored records for an inode with exact UTF-8 names, raw flags, storage forms, and logical lengths. `open_xattr` reads inline binary attributes and inline FinderInfo. `open_resource_fork` reads the raw stored fork. Sonoma 14.7.2 stores the tested resource fork in a separate stream whose physical extent owner is the inode. Its tested large custom attribute also uses a separate stream, with flag `0x0010` set alongside the stream flag and a physical extent owner equal to that stream ID. Both profiles require continuous, unshared, unencrypted extents with checked ownership. Raw data reads stay within logical size and share the volume budget. FinderInfo stored in an inode extended field and unqualified xattr storage flags return typed errors when opened. [Extended attribute fixture](tests/fixtures/sonoma-xattr-blocks.json)

`hard_links` reads an ordinary regular inode’s recorded names in sibling ID order. It checks the link count and primary parent, each inverse map, and the exact stored name and inode in its parent directory. `lookup_stored_name` checks the selected hard-link entry against its sibling record and inverse map before returning the inode. Each name can open the same inode’s checked data and resource streams. The native fixture’s read-only mount reported inode 17 with three links in different directories, and both forks matched byte for byte under each name. [Hard-link fixture](tests/fixtures/sonoma-hard-link-blocks.json)

The hosted tests exercise directory records, inode metadata, ordinary file data, and attributes as part of A-READ-01 and A-READ-02. Apple’s read-only checker selected XID 4 on the populated images and XID 6 on the fragmented and attribute images. The split tree contains 88 files across nine leaves. The payload fixtures validate a 19,000-byte native file, data from both leaves of the physical extent-reference tree, an empty file, and a symbolic link. The fragmented fixture verifies a file with four nonadjacent physical extents, including unaligned reads across every extent boundary. The attribute fixture checks exact inline, empty, FinderInfo, 9,001-byte external attribute, and 19-byte resource fork payloads against macOS `xattr`. The provenance files record the synthetic inputs and exact native block slices.
